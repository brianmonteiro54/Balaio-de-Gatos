Parte 1 · A diferença que ninguém te explicou

Safety protege a pessoa.
Security protege o sistema.

Em português a gente usa "segurança" pra tudo. Em inglês, no contexto de IA, são duas coisas distintas, e cair na pegadinha custa pontos na prova.

01 · Safety × Security

Toggle os dois lados pra ver a diferença na prática.

Os dois precisam coexistir. Você pode ter um sistema super seguro tecnicamente (security) mas que recomenda dieta tóxica pra criança (safety quebrada). E vice-versa.

🔁 Onde se encontram: Um sistema com safety boa mas security ruim dá respostas certas, mas vaza dados de pessoas. Um sistema com security boa mas safety ruim nunca vaza nada, só que recomenda coisas perigosas. IA responsável precisa dos dois.

04 · PII · Personally Identifiable Information

Cola um texto e veja o gato caçar dados pessoais em tempo real.

05 · Residência de dados (data residency)

Onde os dados moram não é detalhe, é lei.

Cada país tem suas regras: LGPD (Brasil), GDPR (Europa), HIPAA (EUA saúde), PIPEDA (Canadá). Algumas empresas SÃO obrigadas a manter dados dentro de uma jurisdição específica. Clica nas regiões pra ver os requisitos típicos.

🎯 Como controlar residência na prática

1. Escolha a região certa Bedrock, S3, SageMaker: todos têm Region em todo recurso. Use a região onde a lei manda.
2. Bloqueie outras regiões via SCP Service Control Policy no AWS Organizations. Ninguém cria recurso fora da região permitida.
3. Cuidado com cross-region replication S3 Cross-Region Replication, Aurora Global Database: ótimos pra DR, péssimos pra residência. Configure com cuidado.
4. Modelos do Bedrock Nem todo FM está em todas as regiões. Confira a tabela de model availability antes de prometer compliance.

📋 SageMaker Model Cards

Documentação estruturada do modelo que vive junto dele. Inclui:

  • Dados de treino (origem, período, tamanho)
  • Casos de uso pretendidos
  • Limitações conhecidas
  • Métricas de performance e bias
  • Histórico de aprovações e revisões

📜 Logging de invocação no Bedrock

Habilita logging em S3 e/ou CloudWatch Logs:

  • Prompt enviado (com PII redacted)
  • Resposta gerada
  • Tokens consumidos (input + output)
  • Latência
  • Identidade da chamada (IAM principal)

🛡️ Bedrock Custom Service Role

Em vez de IAM "wide-open", crie uma role dedicada com escopo mínimo:

  • Permite só os modelos que sua app usa
  • Limita ações (Invoke vs ListModels)
  • Condicionada a tags, IPs, horários
  • Auditável via CloudTrail

🌐 SageMaker Network Isolation

Roda jobs de treino e endpoints em VPC privada sem internet:

  • Sem acesso a S3 público
  • Sem download externo de pacotes
  • Comunicação via VPC Endpoints
  • Obrigatório em ambientes regulados
10 · Cola final pra prova

O que decorar.

🛡️ Safety × Security

Safety resguarda a pessoa (não recomendar dieta perigosa). Security resguarda o sistema (não vazar dados, não deixar invadir). IA responsável precisa dos dois.

💉 Prompt Injection

Atacante insere instruções no input pra sequestrar o modelo ("ignore as instruções anteriores..."). Defesa: Bedrock Guardrails (Prompt attack), validação de input/output.

🔓 Jailbreak

Engana o modelo pra quebrar suas próprias regras (DAN, role-play, hipóteses). Defesa: prompt template fechado + Guardrails + revisão de output.

👻 Adversarial Prompting

Input projetado pra fazer o modelo errar de forma específica. Ex.: token sutil que muda classificação. Defesa: testing adversarial, ensemble, monitoramento.

🚪 Bedrock Guardrails

6 categorias: denied topics, content filters, word filters, PII, contextual grounding, prompt attack. Aplica entrada e saída.

🆔 PII

Trio: Macie (descoberta em S3), Comprehend (texto livre), Bedrock Guardrails (FMs). Detecta + redacta antes de virar log/treino.

🌎 Residência

Cada dado precisa ficar na Region certa. Use SCPs no Organizations pra forçar. Cuidado com cross-region replication automática.

♻️ Retenção

S3 Lifecycle faz a transição automática (Standard → IA → Glacier → Delete). Definir prazo por tipo de dado é base de governança.

📋 Model Cards

Documentação estruturada do modelo (treino, uso, limitações, métricas). Vive no SageMaker, parte de IA responsável e governança.

📜 Logging Bedrock

Habilita em S3 ou CloudWatch Logs. Registra prompt + resposta + tokens + identidade. Imprescindível pra auditoria e debug.

🛡️ Custom Service Role

IAM role dedicada ao Bedrock com escopo mínimo (modelos específicos, ações limitadas, condicionais). Princípio do least privilege.

🌐 Network Isolation

SageMaker treino e endpoints rodam sem acesso à internet. Comunicação só via VPC Endpoints. Padrão em setores regulados.

🎯 Pegadinhas que caem na prova

  • Safety vs Security não é mesma coisa, questões de prova testam a distinção.
  • "Ignore as instruções anteriores e ..." → prompt injection. Mitigação: Bedrock Guardrails (Prompt attack).
  • "Filtrar PII em S3" → Macie. "Filtrar PII em texto" → Comprehend. "Filtrar PII em entrada/saída de FM" → Bedrock Guardrails.
  • Empresa regulada precisa que dados não saiam da Europa → escolher Region eu-* + SCP bloqueando outras regiões.
  • "Documentar transparentemente o modelo" → SageMaker Model Cards. Não é só metadata, é documentação estruturada.
  • SageMaker job não pode acessar internet pública → Network Isolation Mode + VPC Endpoints.
  • Auditoria pede log de quem chamou Bedrock → CloudTrail (chamadas API) + Bedrock invocation logging (prompt/resposta) + CloudWatch Logs.
