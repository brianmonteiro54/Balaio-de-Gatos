Parte 1 · Operação e auditoria

O modelo em produção
precisa de rastro.

02 · Onde cada coisa é logada

Quatro canais, cada um com sua função.

Logging de IA na AWS não é um lugar só. É uma combinação de CloudTrail (quem chamou), CloudWatch Logs (o que aconteceu), S3 Data Capture (input + output completos) e Model Monitor (qualidade/drift).

03 · Model Cards · documentação de modelos

A RG do modelo.

Model Card é documentação estruturada que descreve o modelo: pra que serve, em que dado foi treinado, em quem funciona bem, em quem falha, riscos, métricas, donos. Inspirado no paper "Model Cards for Model Reporting" (Mitchell et al., 2019). AWS implementa via SageMaker Model Cards.

🤔 Por que existe?

  • Auditoria · regulador (BACEN, ANS, ANPD, EU AI Act) pede documentação do modelo
  • Reprodutibilidade · 6 meses depois, você esquece como treinou
  • Comunicação · time de produto/legal/risk precisa entender sem ler código
  • Onboarding · novo dev no time entra mais rápido
  • Compliance · ISO/IEC 42001 (AI management) requer

📑 As 9 seções padrão

  1. Detalhes do modelo · nome, versão, dono, data, framework
  2. Uso pretendido · pra que SIM e pra que NÃO usar
  3. Fatores · grupos demográficos, condições ambientais, instrumentação
  4. Métricas · acurácia, F1, AUC, MAE, etc. (e por subgrupo)
  5. Dataset de avaliação · de onde veio, como foi balanceado
  6. Dataset de treino · idem (pode ser parcial por privacidade)
  7. Análises quantitativas · gráficos, matriz de confusão, viés
  8. Considerações éticas · risco, dano potencial, mitigação
  9. Recomendações · uso seguro, monitoramento, limites

☁️ Como a AWS implementa

  • SageMaker Model Cards · cria, versiona, aprova, exporta PDF
  • Integração · com Model Registry, Pipelines, Studio
  • Aprovação · rascunho → review → publicado
  • API · CreateModelCard, UpdateModelCard, ExportModelCard
  • AI Service Cards · cards públicos da AWS pra Rekognition, Comprehend, etc.

Parte 2 · Customização do modelo

Fine-tuning e os botões
do treino.

Quando RAG e prompt não bastam, você ajusta o modelo. Mas tem 4 jeitos diferentes de fazer isso, com custos muito diferentes.

05 · Ajuste fino (Fine-tuning)

Pegar um modelo pronto e moldar aos seus dados.

Você não treina do zero (custaria milhões). Pega um foundation model pré-treinado (Llama, Titan, Falcon...) e continua o treino com seus dados, ajustando os pesos. Resultado: modelo customizado pro seu domínio sem reinventar a roda.

✅ Quando vale a pena

  • Tom de voz, estilo, persona da marca
  • Formato de saída fixo (SQL custom, JSON com schema próprio)
  • Jargão de domínio (médico, jurídico, financeiro)
  • Idioma de baixo recurso ou variante regional
  • Few-shot já não cabe no contexto

❌ Quando NÃO vale

  • Conhecimento factual que muda (use RAG)
  • Você não tem ≥100 exemplos de qualidade
  • Resolveu com prompt engineering simples
  • Privacidade exige que o dado nunca toque os pesos
  • Você ainda não validou o problema com um piloto

08 · Hiperparâmetros

Os botões do treino.

Hiperparâmetros são as configurações que você define antes do treino, diferente de parâmetros (pesos), que o treino aprende. Mexa nos sliders e veja a curva de loss reagir + o veredicto.

1e-6 (lento, seguro) ··· 1e-2 (rápido, instável)
2 (ruidoso, generaliza) ··· 512 (estável, GPU pesada)
poucas (underfit) ··· muitas (overfit)
0 (decora) ··· 0.5+ (regulariza demais)

09 · Hyperparameter tuning automático

Quando você não sabe o valor certo.

Em vez de chutar manualmente, você define um range pra cada hiperparâmetro e o serviço explora combinações. Cada estratégia tem trade-off entre custo (jobs gastos) e qualidade do resultado.

12 · Cola final pra prova

Tudo o que decorar.

📜 Logging de inferência

Combinação: CloudTrail (auditoria de API), CloudWatch (app logs), Data Capture (input/output em S3), Model Monitor (qualidade/drift).

🟪 Bedrock invocation logging

Liga no console: prompts e respostas vão pra CloudWatch ou S3. Útil pra auditoria, fine-tuning, debugging. Pode conter PII, restringe acesso.

🛡️ Guardrails trace

Mostra o que cada filtro detectou em cada chamada. Combina com CloudWatch. Indispensável pra entender por que algo foi bloqueado.

📋 Model Cards

Documentação estruturada do modelo. 9 seções padrão. AWS: SageMaker Model Cards. Versionamento + aprovação + export PDF.

📑 AI Service Cards

Cards públicos da AWS pra serviços gerenciados (Rekognition, Comprehend, etc.). Documenta limites, casos de uso seguros e considerações éticas.

🔥 Full Fine-tuning

Atualiza todos os pesos. Caro (GPU + horas), poderoso, exige muito dado. Modelo customizado é seu.

🪶 PEFT / LoRA

Atualiza só uma fração (~0.1-3% dos pesos via matrizes low-rank). 10-100× mais barato. Default em fine-tuning moderno.

🎓 Instruction Tuning

FT supervisionado em pares (instrução, resposta ideal). Ensina o modelo a seguir instruções genericamente. Base do "Chat" dos LLMs.

🎯 RLHF

Reinforcement Learning from Human Feedback. Humano ranqueia respostas, treina modelo de recompensa, RL otimiza. Caro mas mais preciso.

📈 Learning rate

Quão grande é cada passo do gradient descent. Baixo = lento. Alto = instável (NaN). Sweet spot tipicamente 1e-5 a 1e-3.

📦 Batch size

Quantos exemplos por step. Pequeno = ruidoso, generaliza melhor. Grande = estável, GPU-pesado. Trade-off com learning rate.

🔁 Epochs

Quantas vezes vê o dataset inteiro. Poucas = underfit. Muitas = overfit. Use early stopping baseado em val loss.

🛡️ Regularização

Dropout (zera neurônios), L1/L2 (penaliza pesos grandes), data augmentation. Combate overfitting.

🎯 SageMaker AMT

Automatic Model Tuning. 4 estratégias: Random, Grid, Bayesian (default), Hyperband. Define ranges, AMT acha o melhor.

💬 Prompt Engineering

Reescreve a pergunta. Não muda modelo, não muda dado. Custo zero, mais simples e rápido. Sempre tente isso primeiro.

📚 RAG

Recupera trechos da sua base e injeta no prompt. Ideal pra conhecimento factual que muda. Não treina modelo.

🛠️ Fine-tuning

Ajusta pesos com seus dados. Ideal pra tom, estilo, formato, jargão. Caro, mas vira ativo da empresa.

🤝 Combinação

Caso real geralmente combina os 3: FT pro tom + RAG pro fato atualizado + Prompt pro formato fechado.

🎯 Pegadinhas que caem na prova

  • "Auditar todas as chamadas pra um endpoint" → CloudTrail + Data Capture pro payload completo. CloudWatch é app log, não API audit.
  • "Vamos retreinar e precisamos saber o que o modelo viu" → Data Capture em S3 (input + output). Sem isso, você reconstrói às cegas.
  • "Modelo bloqueou e o usuário reclamou" → habilite Guardrails trace. Mostra qual filtro pegou.
  • "Documentar pra auditor regulatório" → SageMaker Model Cards. Não confunda com Model Registry (que versiona binário).
  • "Adaptar tom de voz" → fine-tuning. "Conhecimento atualizado" → RAG. "Pequeno ajuste de saída" → prompt.
  • "Pouco dado pra fine-tuning" → use PEFT/LoRA (precisa menos exemplos) ou volte pra few-shot.
  • "Loss sobe ao infinito (NaN)" → learning rate alto demais. Reduza ou use warmup.
  • "Train loss baixo, val loss alto" = overfitting. Mais dropout, mais dado, menos epochs.
  • "Quero menor número de jobs no tuning" → Bayesian Optimization. Hyperband é pra economizar GPU em jobs longos.
  • RLHF ≠ instruction tuning. RLHF usa reward model + RL. Instruction tuning é supervised fine-tuning em pares (instr, resp).
  • Custom Model no Bedrock só roda em Provisioned Throughput (capacidade reservada). Sob-demanda não rola.
  • Bedrock Knowledge Bases ≠ Bedrock Custom Models. KB é RAG. Custom é Fine-tuning. Misturar é erro clássico.
  • "Resposta tem que ser 100% factual e citar fonte" → RAG, não fine-tuning. FT pode "lembrar errado".
  • Hiperparâmetros são definidos por você, parâmetros (pesos) são aprendidos pelo treino. Aparece direto na prova.
  • Quase sempre comece com Prompt Engineering. Sobe pra RAG se faltar conhecimento. Sobe pra FT só se for um problema de comportamento que prompt não resolve.
