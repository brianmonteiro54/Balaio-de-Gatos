Parte 1 · Embeddings, similaridade e RAG vs Fine-tuning

Como o gato vira número
e acha quem é parecido.

Antes de falar em métrica e deploy, é preciso entender como o conhecimento entra no modelo. Por embedding (representação vetorial) ou por treino (fine-tuning). Cada um com seu custo e momento certo.

01 · RAG × Fine-tuning

Adicionar conhecimento ou mudar comportamento?

Erro clássico de prova: confundir os dois. RAG recupera contexto na hora, não treina o modelo. Fine-tuning ajusta os pesos com seus dados, vira parte do modelo. Clica num cenário e descubra qual técnica resolve.

📚 RAG 🛠️ Fine-tuning
Muda os pesos? ❌ Não ✅ Sim
Atualizar dado é ✅ Re-indexar (segundos) ⏳ Re-treinar (horas/dias)
Custo 💲 Baixo (busca vetorial) 💲💲💲 Alto (GPU + dados)
Boa pra Conhecimento factual, atualizado, com citação Estilo, tom, formato, jargão, comportamento
Risco principal Retrieval ruim → resposta ruim Overfitting → perde generalização

03 · Similaridade vetorial

Como medir "perto" entre vetores?

A métrica padrão de vector DBs é cosseno: mede o ângulo entre os vetores, ignorando comprimento. Vai de -1 (opostos) a 1 (idênticos). Mexa nos vetores e veja a similaridade ao vivo.

Arrasta as bolinhas pra mover os vetores.

≈ idênticos
Cosine similarity 0.97
Ângulo (graus) 14°
Distância euclidiana 42
Dot product 21000

"Gato" e "felino" são quase sinônimos. Vetores quase paralelos → cosseno alto.

📐 Métricas comuns:
  • Cosseno · padrão em texto · ignora magnitude
  • Euclidiana · distância "real" · sensível à escala
  • Dot product · simples e rápido · usa magnitude
  • Manhattan · soma dos eixos · resistente a outliers

05 · Quando usar embeddings

Nem toda busca precisa de vetor.

Embedding brilha quando a relação é semântica (significado, não palavra). Pra busca exata, SQL e índices clássicos ainda ganham. Lê o cenário e adivinha.

1 / 6 🔥 0

📋 Quando vai de embedding

  • ✅ "Encontre conteúdo parecido" (semântico)
  • ✅ Recomendação por similaridade
  • ✅ Detecção de duplicatas/anomalias
  • ✅ Multi-idioma (vetor cruza idiomas)
  • ✅ Multimodal (imagem ↔ texto)

🚫 Não precisa de embedding

  • ❌ Busca exata por ID, CPF, código
  • ❌ Filtros por intervalo numérico/data
  • ❌ JOIN entre tabelas relacionais
  • ❌ Resultado precisa ser determinístico
Parte 2 · Métricas

Treinou. Mas é bom?
Mede direito, não chuta.

Acurácia parece simples, mas mente. Em dataset desbalanceado, 99% de acerto pode ser fracasso. Aqui vai a régua de cada métrica e quando usar.

06 + 07 · Matriz de confusão · Acurácia · Precisão · Recall · F1

A base e as quatro métricas que ela explica.

Quatro caixas: VP e VN são acertos, FP (alarme falso) e FN (deixou passar) são os dois jeitos diferentes de errar, e quase sempre custam coisas diferentes. Mexa nos sliders e veja a matriz reagir junto com as 4 métricas de classificação. Cada métrica responde a uma pergunta de negócio diferente.

"detectou gato mas era cachorro"
"era gato mas o modelo deixou passar"
"era cachorro e o modelo disse que era cachorro"

📐 As 4 métricas, ao vivo

📊 Acurácia
(VP + VN) / Total
90%

Pergunta: "De todas as previsões, quantas acertei?"

⚠️ Mente em dataset desbalanceado.

🎯 Precisão
VP / (VP + FP)
94.4%

Pergunta: "Dos que previ como positivos, quantos eram?"

⚠️ Use quando FP é caro: spam, denúncia de fraude.

🪤 Recall
VP / (VP + FN)
85%

Pergunta: "Dos casos reais positivos, quantos peguei?"

⚠️ Use quando FN é caro: detecção de tumor, gato perdido.

⚖️ F1 Score
2 · (P · R) / (P + R)
89.5%

Pergunta: "Tô equilibrado entre Precisão e Recall?"

✅ Boa métrica única em dataset desbalanceado.

🎢 O trade-off Precisão × Recall

Quase sempre aumentar uma diminui a outra. Deixar o modelo "mais agressivo" (chutar positivo com pouca certeza) sobe Recall mas derruba Precisão. F1 é o equilíbrio. ROC-AUC é a métrica resumo da capacidade do modelo em qualquer threshold.

08 · Threshold (intervalo de decisão)

O corte que vira "sim" ou "não".

O modelo cospe um score de 0 a 1 (probabilidade). Quem decide se vira positivo é o threshold. Mover o corte muda Precisão, Recall e a matriz inteira. Mexa o slider e veja a régua dos gatos.

← captura tudo (recall ↑)só certeza (precisão ↑) →
Precisão 88.0%
Recall 79.2%
F1 83.4%
Detectados 42 / 50
💡 Como escolher
  • Threshold baixo (0.2-0.4) → cataloga mais, mais alarme falso. Use quando FN é caro (saúde, segurança).
  • Threshold alto (0.7-0.9) → só pega certezas, deixa muita coisa passar. Use quando FP é caro (spam, denúncia).
  • 0.5 só é certo se o dataset é balanceado e os erros custam o mesmo.
09 · MAE · MSE · RMSE · R²

Quando o modelo prevê número.

Em regressão, o erro é a distância entre o previsto e o real. Cada métrica trata essa distância diferente. Mexa nas previsões dos 10 gatos e veja as métricas se ajustando.

Arrasta as bolinhas reais (verdes) pra mudar o erro de cada amostra.

📏 MAE Mean Absolute Error 0.42

Média do módulo dos erros. Mesma unidade do alvo (kg). Robusto a outliers.

(1/n) · Σ |yi − ŷi|
📐 MSE Mean Squared Error 0.31

Média do quadrado dos erros. Penaliza erro grande mais que pequeno. Unidade ao quadrado (kg²).

(1/n) · Σ (yi − ŷi)²
📊 RMSE Root Mean Squared Error 0.55

Raiz do MSE. Volta pra unidade original (kg). É a métrica mais lida em produção.

√MSE
🎯 R² Coeficiente de determinação 0.82

Quanto da variância dos dados o modelo explica. 1.0 = perfeito. 0 = chuta a média. < 0 = pior que a média.

1 − (Σ erros² / Σ var)
10 · Métricas de negócio

O número que decide se o projeto continua.

F1 alto não paga conta. Quem aprova budget olha ROI, custo evitado, receita gerada e impacto operacional. Use a calculadora pra ver o detector de gato perdido virar dinheiro.

🎛️ Variáveis do caso

💡 Métricas de negócio que caem na prova

  • ROI = (ganho − custo) / custo · em %. Acima de 0 vale a pena, regra de bolso é mirar >30%.
  • Custo evitado = quanto deixou de gastar (ex.: gato perdido não rende reembolso de plano).
  • Receita gerada = vendas/leads que vieram do modelo. Use teste A/B pra atribuir.
  • Impacto operacional = horas humanas economizadas, redução de tempo de resposta, NPS.
  • Custo por inferência = total de gasto / chamadas do mês. Compare com receita por chamada.
Parte 3 · Tipos de inferência

Treinou o gato. Hora
de ele trabalhar.

Inferência é o "modelo em produção respondendo". Tem 4 sabores no SageMaker, e a escolha errada custa caro ou deixa o usuário esperando.

11 · Inferência em lote × tempo real

Processa tudo de uma vez ou um por um?

A pergunta-chave é simples: o usuário tá esperando? Se sim, real-time. Se não, batch, e você economiza muito.

📦 Batch (em lote)

Processa milhares juntos, fora do horário

  • ✅ Sem endpoint sempre ligado · você paga só o job
  • ✅ Otimizado pra throughput (volume)
  • ✅ Roda offline · usuário não espera
  • ⚠️ Latência: minutos a horas
  • ⚠️ Resultado vem num arquivo (S3) depois
Use quando: rodar todo fim de semana scoring de churn, classificar 10M de fotos antigas, recalcular embeddings da base inteira.
AWS: SageMaker Batch Transform
⚡ Real-time

Responde uma chamada por vez, em ms

  • ✅ Latência baixa (50-500ms)
  • ✅ HTTPS endpoint sempre disponível
  • ✅ Auto-scaling configurável
  • ⚠️ Paga pela instância 24/7 mesmo parada
  • ⚠️ Custo alto se volume é baixo
Use quando: chatbot, busca em loja, recomendação durante navegação, fraude em pagamento, qualquer caso com usuário esperando.
AWS: SageMaker Real-time Endpoint

🤔 Cenário rápido

"Quero recalcular o score de saúde de todos os 2M de gatos do sistema toda madrugada de domingo."

12 · Serverless × Endpoint dedicado

Pagar por chamada ou pela máquina ligada?

Mesma pergunta de Lambda × EC2, mas pra inferência. Serverless escala a zero. Endpoint tem instância sempre quente. Escolha errada = ou conta cara, ou usuário esperando o cold start.

13 · Inferência assíncrona

Quando a chamada demora demais pra esperar.

Async é o meio-termo: você manda a request, recebe um token de fila, faz outra coisa, e quando o resultado tá pronto cai num bucket S3 (ou recebe notificação SNS). Útil pra payloads grandes (vídeo, PDF longo) ou inferências que levam minutos.

1 📤 Cliente envia POST com input (S3 path)
→
2 🎫 Recebe token jobId + S3 output path
→
3 ⚙️ SM processa na fila interna, sem timeout HTTP
→
4 📥 Resultado em S3 + notif SNS opcional

✅ Use Async quando

  • Payload > 6MB (limite do real-time)
  • Inferência demora > 60s (timeout do real-time)
  • Vídeo, PDF longo, audio extenso
  • Usuário aceita esperar minutos por e-mail/notif
  • Quer escalar a zero (sem requisição = sem custo)

⚠️ Não use Async quando

  • Usuário tá vendo a tela esperando resposta
  • Latência precisa ser previsível em ms
  • Aplicações conversacionais (chat)
  • Resposta tem que voltar na mesma chamada HTTP

🗺️ Os 4 modos de inferência no SageMaker

⚡ Real-time HTTPS · ms · 24/7
☁️ Serverless HTTPS · ms · escala a zero
⏳ Async fila · minutos · payload grande
📦 Batch Transform job · horas · volume gigante

16 · Amazon Bedrock · visão geral

FMs como serviço, sem servidor pra cuidar.

Bedrock é a API gerenciada de Foundation Models. Você escolhe o modelo (Claude, Titan, Llama, Mistral, Cohere, Stability), chama API, paga por token. Sem GPU, sem cluster, sem deploy. Clica em cada feature pra entender.

⚔️ SageMaker × Bedrock · onde cada um brilha

🟧 Use SageMaker quando
  • Quer treinar modelo do zero
  • Tem dados tabulares · ML clássico
  • Precisa de pipeline MLOps full
  • Quer controle total da infra
  • Vai operar modelo customizado em escala
🟪 Use Bedrock quando
  • Quer GenAI sem operar GPU
  • Precisa de RAG rápido (Knowledge Bases)
  • Quer agente com ferramentas
  • Precisa de guardrails de segurança prontos
  • Tem time pequeno e quer time-to-market

📌 Os dois convivem. Ex.: detector de gato (clássico) no SageMaker + chatbot do app (GenAI) no Bedrock + Knowledge Base apontando pro S3 da empresa.

17 · Cola final pra prova

Tudo o que decorar.

🔁 RAG × Fine-tuning

RAG: dado novo/factual, atualizado, com citação. FT: tom, estilo, formato, jargão, comportamento. RAG não treina, FT muda os pesos.

🔢 Embedding

Vetor de N dimensões representando significado. Coisas parecidas → vetores próximos. Mesmo modelo de embedding em ingest e query.

📐 Cosseno

Métrica padrão de similaridade. Vai de -1 a 1. Ignora magnitude. 1 = idênticos.

🗄️ Vector DB

OpenSearch (k-NN), Aurora pgvector, RDS Postgres, Neptune Analytics, DocumentDB, MemoryDB. Bedrock KB gerencia.

🤔 Embedding ou SQL?

Semântico → embedding. Exato/intervalo/JOIN → SQL. Se quer os dois, híbrido (BM25 + vetor).

🟧 Matriz de confusão

VP, FP (alarme falso), FN (deixou passar), VN. FP × FN custam coisas diferentes. Pense no negócio antes da fórmula.

🎯 Precisão × Recall

Precisão: dos previstos como pos, quantos eram? Use se FP é caro. Recall: dos reais pos, quantos peguei? Use se FN é caro.

⚖️ F1 Score

Média harmônica de P e R. Boa métrica única em dataset desbalanceado.

📊 Acurácia

(VP+VN)/Total. Mente em dataset desbalanceado. Não use sozinha.

📏 Threshold

Corte do score. Baixo → mais recall. Alto → mais precisão. Escolha por custo de erro, não por padrão (0.5 ≠ certo sempre).

📈 MAE × MSE × RMSE

MAE: módulo do erro, robusto. MSE: erro ao quadrado, pune outlier. RMSE: √MSE, mesma unidade do alvo.

🎯 R²

Quanto da variância o modelo explica. 1=perfeito, 0=média, <0=pior que média.

💰 Métricas de negócio

ROI, custo evitado, receita gerada, impacto operacional, custo por inferência. Quem aprova budget olha pra essas.

📦 Batch × Real-time

Batch: volume, sem usuário esperando, S3 → S3, paga só o job. Real-time: HTTPS ms, paga 24/7.

☁️ Serverless × Endpoint

Serverless: escala a zero, cold start. Endpoint: sempre quente, paga a instância. Volume baixo → serverless.

⏳ Async

Payload >6MB ou inferência >60s. Volta resultado em S3 (+ SNS). Escala a zero, sem timeout HTTP.

🛒 API × Auto-hospedado

API (Bedrock, Comprehend): pago por uso, time pequeno. Auto: VPC própria, time MLOps, escala muito grande.

🟧 SageMaker

Plataforma completa de ML: prep → treino → deploy → monitor. Studio, Wrangler, Ground Truth, Feature Store, AMT, Autopilot, JumpStart, Endpoints, Model Monitor, Clarify, Pipelines.

🟪 Bedrock

FMs como serviço. InvokeModel, Playground, Knowledge Bases (RAG), Agents (ReAct), Guardrails, Custom Models (FT), Model Evaluation, Provisioned Throughput.

⚔️ SM × Bedrock

SageMaker = treino e operação. Bedrock = GenAI gerenciada. Convivem no mesmo projeto.

🎯 Pegadinhas que caem na prova

  • "Acurácia 99% é incrível" → desconfia. Pergunta se o dataset é balanceado. Se 99% é "não-fraude", chutar "não-fraude" dá 99%.
  • "Reduzir falsos negativos" → otimize Recall, NÃO Precisão. "Reduzir falsos positivos" → Precisão.
  • "RMSE é em qual unidade?" → na mesma do alvo (kg, $, min). MSE é ao quadrado, MAE é módulo.
  • "R² negativo" não é erro: o modelo é pior que prever a média.
  • "Conhecimento muda com frequência" → RAG. "Adaptar tom de voz" → fine-tuning. "Jargão de domínio" → continued pre-training.
  • Cosseno é a métrica padrão em texto. Euclidiana é mais comum em imagens. Manhattan resiste a outliers.
  • "Payload de 8MB" ou "inferência demora 2 minutos" → Async, não real-time.
  • "Tráfego raro/dev/test" → Serverless. "Latência crítica e tráfego constante" → Real-time endpoint.
  • "Toda madrugada processar X milhões" → Batch Transform.
  • SageMaker treina e operaciona modelos. Bedrock só roda FMs gerenciados (não treina do zero).
  • Bedrock Knowledge Bases ≠ Fine-tuning. Knowledge Bases é RAG gerenciado. Custom Models é FT.
  • Provisioned Throughput (Bedrock) ≈ Real-time Endpoint (SageMaker): capacidade reservada, custo fixo, latência baixa.
  • Métrica de negócio > métrica técnica. F1=0.95 não justifica projeto se ROI é negativo.
